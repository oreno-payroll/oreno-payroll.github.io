# Payroll（OneDrive暗号化給与明細管理）

本業・副業の給与・賞与PDFを解析し、入力済み明細とPDF原本を**暗号化してOneDriveのアプリ専用領域へ保存**します。Microsoft認証とMicrosoft Graph APIを使用し、給与の平文PDF・平文JSONをOneDriveへアップロードしません。旧給与明細IndexedDBは移行・整理専用であり、通常の永続保存先ではありません（任意で有効にする「このブラウザを記憶」の専用IndexedDBとは別物です）。

Payrollは本人の給与明細管理と年末調整サポートを提供し、本人用の解析済み収入だけを別アプリのFinanceへ公開します。家計簿・支出管理・月別収支分析はFinance側の役割です。

## 画面・実装

- `src/main.ts`：ホーム画面、支給額集計と保存済みPDF一覧、年度末までの見込み表示
- `src/forecast/annualForecast.ts`：保存データを変更せず、通常給与は直近最大3件の中央値・本業賞与は最新の通常給与1件を使って見込みを算出
- `src/upload.ts`：複数PDFの解析、入力確認、重複スキップ付き一括保存
- `src/edit.ts`：保存済み明細の編集。古いタブからの上書きを防止
- `src/backup.ts`：暗号化バックアップ作成、旧ZIP/暗号化形式の復元
- `src/pdf/`：PDF.jsによる座標診断・給与/賞与の書式解析
- `src/storage/`：明細の入出力・入力検証、旧IndexedDBの移行と整理、ZIP・バックアップ、PDF原本検査
- `src/cloud/`：Microsoft認証、Graph経由のOneDrive保存、AES-GCM暗号化、年度ごとの明細管理、Finance連携用収入ファイルの生成。`auth.ts`は解除方法の選択、`rememberedBrowser.ts`はブラウザに記憶した非抽出鍵を管理
- `src/yearEnd/`・`src/year-end-assist.ts`：従業員別の年末調整サポート。本人の明細とは独立して管理
- `public/`：HTMLとCSS。`dist/`はビルド生成物なので編集しません

## Macでの実行

```bash
cd ~/Documents/payroll
npm ci
npm run check
npm run build
npm test
python3 -m http.server 5000 --directory dist
```

ブラウザで `http://localhost:5000/` を開きます。Microsoft EntraのSPAリダイレクトURIへ`http://localhost:5000/auth/redirect.html`を登録してください。`localhost` と `127.0.0.1` や異なるポートは別オリジンなので、同じホスト名でアクセスしてください。開発中の自動ビルドには `npm run dev` を利用できます。

## 保存・重複

- 1回のアップロードでは最大30件、各PDF最大25MiB。保存済み原本は1件最大50MiB（旧データとの互換）。原本の合計容量は最大480MiB、明細は最大2000件です。
- 同一PDF（SHA-256）または「勤務先・明細種別・対象年月」が一致すると重複扱いになります。
- **既存データを優先し、重複分だけスキップ**。10件中1件が既存データと重複すれば、新規9件だけ保存し、保存後にスキップした項目を通知します。
- 同時投入の中に重複があれば、先に並んだ1件を保存して、後の重複をスキップします。
- 既存データや手動編集済みの金額、PDF原本を重複保存で置換しません。
- 保存時はPDF原本を暗号化してOneDriveへ保存・読み戻し照合してから解析済み明細を確定します。OneDriveの複数ファイル更新は単一トランザクションではないため、途中失敗時には暗号化ファイルが一部残る可能性があります。
- 保存済み明細を編集すると更新番号が進みます。別タブで編集が確定していた場合、古いタブからの保存を拒否します。
- 編集で年月・種類が別の保存済み明細と重なる場合は、利用者の確認後に重複明細を論理削除します。対象の暗号化PDF原本はOneDriveに保持します。これはアップロード時の重複スキップとは別です。

## 暗号化バックアップ（v1）

- 1個の従来ZIP（`manifest.json` と `pdf/`原本）をブラウザ標準の **AES-256-GCM** で丸ごと暗号化します。
- 鍵導出は **PBKDF2-HMAC-SHA256・600,000回、ランダムsalt 16バイト**。GCM nonce/IVはファイルごとに乱数12バイト。ヘッダーは認証追加データ（AAD）で保護します。
- 書出ファイルの拡張子は `.payroll`。一般のZIP解凍ソフトでは直接開けません。バックアップのパスワードは永続保存せず、忘れると復元できません。
- **以前作成した無暗号 `.zip` もインポート可能**。ZIP内部のschemaVersionは1のままです。
- 復元時は復号→ZIP構造/CRC→PDFのSHA-256→PDF.jsでの解析→メタデータ・金額・容量チェックの後、ユーザーの確認を経てOneDrive上の明細を更新し、余剰明細を論理削除します。既存の暗号化PDF原本は自動消去しません。
- 最大ZIP 512MiBに対して保存可能PDF合計を480MiB以下に制限し、保存済みでバックアップ不能になる事態を防ぎます。
- ZIP生成・暗号化・復元では、一時的に原本と同程度以上のメモリを使用します。大容量バックアップにはメモリ余裕のある端末を使ってください。
- `.payroll` バックアップの暗号化とOneDrive保管庫の暗号化は別の仕組みです。閲覧するブラウザやオリジンの管理にも注意してください。

## 安全運用

- 重要な更新や明細整理の前には、最新のOneDrive明細から `.payroll` バックアップを作成し、安全な別の場所へ保管してください。
- 新版の `.payroll` を作成後、**別のブラウザプロファイルなどの空の環境でテスト復元**できると安心です。既存データがある状態で安易に全件復元しないでください。
- 明細の保存・編集・削除ではOneDrive上の暗号化データを更新します。**給与明細本体はブラウザのサイトデータには保存しません**。ただしMicrosoft認証キャッシュ・SharedWorkerの一時鍵・明示的に記憶したブラウザ鍵はブラウザの状態に依存するため、サイトデータを消すと再ログイン・パスフレーズ再入力が必要になり得ます。誤削除・アカウント間違い・鍵紛失に備え、定期的にバックアップしてください。
- `node_modules`、`dist`、PDF原本、ZIP、`.payroll` はGit管理に含めない設定です。

## 年度見込み（ホーム専用）

ホームの「3月まで見込み」をONにすると、現在年度の未登録の通常給与を、勤務先別の直近3件の中央値を使って表示用の合計に加算します。本業のみ8月・翌2月の未登録賞与を、月給の交通費と立替経費を除いた額面・手取りを用いて参考推計します。既に登録済みの本業賞与がある月には加算しません。副業の将来賞与は予測しません（保存済みの副業賞与実績は「賞与を含む」ON時に集計）。通常給与の過去未登録月は補完しません。チェック状態と見込み額は保存されません。

## 例外帳票と個別確認（2026-11-12）

- 本業の「通勤手当/非課」「非課税通勤費」と「立替経費」が同月に存在するときは、**交通費と立替経費を別々に保存**します。税区分の帳票検算では、両者の合計を非課税支給額として使います。
- 本業に「立替経費」しか存在しない場合は、交通費として全額保存し、経費欄は空欄にします。経費と交通費の内訳は推測しません。
- 将来の月給予測では経費精算を繰り返すと仮定せず除外し、本業賞与の見込みでは交通費・経費の両方を除外します。
- 既に保存済みの明細の内訳は自動的に書き換えません。編集画面で交通費・立替経費の項目を修正できます。
- 「年調過不足税額」は通常の所得税と独立して保存する任意フィールドです。負数（還付）を認め、手取り検算の控除内訳にも含めます。ホームの所得税実績は年調を加味し、将来の月給見込みは年調額を参照しません。
- 本業の賞与が0円で、賞与手当・所得税・振込欄が存在しない明細も、上部の差引0円と支給・控除各0円を確認できれば正常な「要確認」明細として保存できます。入力に存在しない控除額を勝手に書き込むことはしません。
- アップロード画面の「要確認」「確認済み」はPDFごとに管理します。警告を確認した明細は別の明細を開いても状態を維持し、当該明細を編集した場合のみ確認を解除します。**警告がある全件を確認済みにするまで一括保存はできません**。PDF解析自体が失敗したファイルは「読み取り失敗」と表示し、保存対象にできません。
- PDF未選択時は追加操作を優先して表示します。読み込み後は内容確認、確認完了後は一括保存の案内へ切り替わります。
- 現在の確認状態はアップロード画面内の未保存一時状態です。保存後の確認記録は明細と一緒に暗号化され、OneDriveへ保存されます。

## 年末調整サポート（本人の明細とは分離）

- `year-end-assist/` 画面で従業員を登録し、暦年ごとの給与・賞与明細（PDF原本と解析/手入力値）を管理します。課税支給額の年間実績と未支給月・賞与の見込み、年度メモも保存できます。
- 年末調整のPDF原本は、通常モードの副業と同様に支給年月と種別から `YYYYMM_給与明細.pdf` / `YYYYMM_賞与明細.pdf` という表示・ダウンロード名を付けます。OneDriveの暗号化原本は衝突を避けるUUID名のまま保持します。以前のUUID表示名も、原本を書き換えず画面上で補完します。
- 年末調整の従業員一覧はプロフィールを上限5件で並行取得し、PDF解析は最大2件、暗号化PDF原本の保存・再取得・復号・SHA-256照合は最大3件ずつ並行します。年度データの確定は、全件照合が成功してから一度だけ行います。Graph側の混雑や端末性能によって速度は変わります。
- 年間課税支給額は未取得月がある場合、通常の補助文言で月を表示します。未取得月の金額は合計に含みません。
- 従業員データはOneDriveの `payroll/year-end-assist/` （鍵変更後は後述の世代別領域）に、専用の暗号化ファイルとして保管します。本人の給与明細・Finance向け収入データには混入しません。
- 設定画面の年末調整専用バックアップでは、従業員・各年度の明細・PDF原本・見込み・メモを別ファイルに書き出します。復元時は同じ従業員を無条件に上書きせず、復元前の検査と競合確認を行います。
- 本人・従業員の復元は「ファイル選択 → パスワード入力 → ファイルを検証 → 確認チェック → 復元する」で操作順を統一しています。本人用の旧ZIPだけはパスワード不要ですが、明示的な検証が必要です。本人の復元は現在の明細を全件置換し、従業員の復元は登録済みデータを上書きせず追加対象のみ復元します。

## OneDrive暗号化保管庫（現行の永続保存）

**Financeの既存ファイルを直接変更しません。** PayrollとFinanceは同じMicrosoftアカウント・Microsoft Entraアプリ登録のClient ID / `Files.ReadWrite.AppFolder` を使ってOneDriveアプリ領域を共有できます。公開ホストが異なる場合、Client IDはPayroll側にも入力します。SPAリダイレクトURIはMSAL v5専用ブリッジ（本番：`https://oreno-payroll.github.io/auth/redirect.html`）をMicrosoft Entraへ登録してください。**先にEntraの登録を追加してからデプロイしてください。** 旧ルートURIは移行完了まで残せますが、Payrollは新しいブリッジURIを使います。**両アプリの保管庫の暗号鍵・パスフレーズは別**です。

### 永続保存

- `payroll/index.enc`：暗号化された年度索引。16バイトのランダムsaltと31万回のPBKDF2-SHA256からAES-256-GCM鍵を導出します。索引は現在の暗号世代（`generation`）と本人の明細年度・収入公開年度を管理します。
- `payroll/statements/YYYY.enc`：対象年月の**給与年度（4月〜翌3月）**ごとの解析済み給与レコード、revision、削除トゥームストーンを暗号化保存。PDFは入れません。
- `payroll/originals/YYYY/MM/<uuid>.enc`：取込時の対象年月に配置した暗号化PDF原本。編集で対象年月を変えても保存先は移動しません。バイト列照合後に明細を確定します。
- `payroll/income/YYYY.enc`：支給日の**暦年**ごとに、明細ID・支給日・対象年月・本業/副業・給与/賞与・手取り・額面・課税支給額（存在する場合）・revisionを公開する、Finance連携専用の暗号化データ。PDFや給与明細の内訳は含みません。
- パスフレーズ変更後は、`payroll/index.enc` の `generation` が指す `payroll/versions/<generation>/` 以下の `statements/`、`originals/`、`income/`、`year-end-assist/` が現行データです。旧世代は安全な照合・整理操作まで保持します。**固定パスの `payroll/income/` は旧世代互換用に残る場合があり、常に最新データとは限りません。**

`index`、`year`、`original`、`income`と年末調整の専用ファイルは `payroll-cloud-envelope-v1` を使い、`kind` とAES-GCMのAADで用途を分離しています。暗号方式の構成はFinanceを参考にしていますが、Financeの既存暗号ファイルを変更・上書きしません。平文のPDFやJSONをOneDriveにアップロードしません。OneDrive側にはファイルサイズ・フォルダ年/月・更新日時などのメタデータが残ります。

### Financeへの収入連携（実装済み）

- Payrollは本人の明細の保存・編集・削除に合わせて、収入公開ファイルを更新します。通信中断などで収入同期だけ失敗した場合は、設定画面の「連携データを再生成」で再同期できます。
- Financeは `payroll/index.enc` を復号し、索引が示す年度と暗号世代の `income/YYYY.enc` を**読み取り専用**で取得します。Payrollで登録済みの収入を月別・年間集計、支給予定や口座残高予測に反映します。PDFを直接解析したり、Payrollのファイルを書き換えたりしません。
- 設定画面の「Finance連携用の収入データ」はPayroll側の公開データの再生成操作です。Financeの同期状態や初回接続を管理する操作ではありません。
- 初回のFinance側連携では、Financeの保管庫を解除してから**Payroll用パスフレーズを別途入力**します。Financeは復号専用の非抽出鍵をセッション中に利用し、次回の自動取得用パスフレーズはFinanceの**暗号化された設定データ**へ保存できます。PayrollがFinanceへ鍵・パスフレーズを送信する仕組みではありません。
- Finance側で自動取得が設定済みの場合、保管庫の解除時や、画面表示中で前回同期から10分以上経過したときに更新を確認します。接続不可・復号失敗時は未同期として扱います。両アプリで同じMicrosoftアカウントとClient IDを利用しているか確認してください。

### Graph通信の一時障害対応

- OneDriveの読み取り用GET/HEADでHTTP 408/429/500/502/503/504または一時的なネットワーク中断が起きた場合だけ、最大2回の追加試行を行います。`Retry-After`の待機指示を優先し、30秒を超える指定では早めの再送をせずエラーとします。指示がない場合は350ms→700msの間隔を取ります。
- 期限切れ認証の401は従来どおり、読み取りでのみトークンの再取得を最大1回行います。**書き込み・削除・アップロード途中のPUTは自動再試行しません。** 重複保存や不明な削除結果を避けるためです。
- 原本の署名付きダウンロードURLもGETだけを同様に再試行し、Bearerトークンを送信しません。不正JSONメタデータの再取得は既存の3回上限を維持します。

### 操作と競合

- 保管庫を開く画面で選ぶ方式は**「記憶しない」**と**「このブラウザを記憶する」**の2種類だけです。従来の「このタブで保持（最長2時間）」は廃止し、復号可能な生の鍵素材を`sessionStorage`に保存しません。旧v1/v2タブ鍵は起動時に削除します。SharedWorkerのメモリによる画面遷移中の鍵共有は維持します（プロセス終了などで消失します）。
- 設定画面では、未登録時は「このブラウザを記憶する」、登録済みなら「記憶を解除」だけを表示します。確認できない場合は登録操作を隠します。
- **「このブラウザを記憶する」**を明示的に選択した場合は、専用IndexedDB（`payroll-remembered-browser-key-v1`）に*取り出し不能（非抽出）のCryptoKey*と最小限の保管庫識別情報を保存します。自動期限はありません。元の復号パスフレーズや給与データは保存しません。同じMicrosoftアカウントでの再接続・索引照合後に自動解除でき、設定画面の「認証」から記憶状態の確認・登録・解除ができます。
- 手動ロックは同一オリジンの他タブにも通知され、自動再解除を抑止します。手動ロック後は利用者の操作で開き直してください。「記憶しない」へ変更すると以前のブラウザ記憶を解除します。鍵保存に失敗した場合は成功扱いしません。**共有端末ではブラウザ記憶を使わないでください。**
- OneDriveの暗号索引の破損・暗号鍵不一致・パスフレーズ変更を区別できないときは、**ブラウザ記憶鍵を自動削除しません**。索引の状態を確認・復旧したうえで再接続してください。必要なら利用者自身が記憶を解除・再登録できます。
- 設定のMicrosoftアカウント欄に「サインアウト」を設けています。明示的な確認後、最初に画面を隠して全Payrollタブをロックします。その後、SharedWorkerの一時鍵と専用IndexedDBのブラウザ記憶鍵を**独立して消去・完了確認**し、両方成功した場合にだけMSALの認証キャッシュ削除とMicrosoftのサインアウト画面への移動を開始します。片方の鍵消去が失敗してももう片方の消去は試し、失敗箇所を通知してロック状態を維持します。Microsoft側の認証初期化・サインアウトが失敗してもローカルの鍵削除は取り消されません。サインアウト後の戻り先として、Microsoft EntraのSPAリダイレクトURIにPayrollのルートURLも登録しておいてください。Financeなど他サイトの認証や、既にダウンロード済みのPDFファイルは操作しません。
- 通常のホーム表示は年別の暗号化解析JSONのみ取得。PDFは閲覧・編集・バックアップ作成時に個別取得します。
- 登録時は原本アップロードと読み戻し照合をしてから、年別解析JSONをETag条件付きで確定。その後、暗号化収入ファイルを更新します。
- 同じ年度の同時更新では、安定した数値IDで3方向マージします。異なる明細・異なる入力項目は統合し、同じ項目の異なる編集や削除と更新が競合した場合には保存失敗として明示します。
- OneDriveに複数ファイルを一度に原子的確定できないため、途中失敗時には一部暗号文が残る可能性があります。**エラーを成功扱いせず**、次の起動・操作で現在のクラウドデータを読み直して復旧してください。
- ホーム・編集画面からの明細削除は、解析済み明細とFinance連携用収入情報から除外する操作です。**暗号化PDF原本はOneDriveに保持されます。**
- 設定の「未参照PDF原本の管理」で、索引と全年度明細に参照されない本人のPDF原本を検査・回収・個別整理できます。削除済み明細だけでなく保存中断で残ったPDFも含まれます。PDF回収後にアップロード画面から再取込できますが、元の手動編集値を含めた明細復元はバックアップから行ってください。
- 原本整理は索引・全年度ETag・原本の復号を再照合し、本人の未参照原本だけをOneDriveのごみ箱へ移動します。**Graphの通常削除は完全消去ではありません。** 完全消去する場合はOneDriveのごみ箱を別途操作してください。年末調整の従業員原本は対象外です。

### 旧IndexedDBの移行・整理

1. 旧DBにしか存在しない明細がある可能性を確認し、必要なバックアップを別の安全な場所に保存してください。
2. **移行・削除のいずれも**OneDriveに接続してPayroll保管庫を解除する必要があります。削除前にはOneDriveの明細と原本PDFを照合します。
3. 設定画面の「旧データの整理・移行」から「旧データを確認・移行」を実行します。
4. 旧IndexedDBを読み取り専用で開き、旧明細IDを保持して原本PDFの暗号文を保存、復号しバイト列を照合します。途中失敗時は中止し、成功していない処理を完了扱いしません。
5. 移行後、明細数・集計金額・PDF閲覧・暗号化バックアップの一致をMac/Galaxyで確認してください。
6. **旧IndexedDBは自動削除されません。** 設定画面の「旧DBを削除」は、OneDriveにある明細と暗号化PDF原本を全件照合し、旧DBのデータと一致した場合に限り実行します。接続できない、未移行のデータがある、照合が完了しない場合は削除を拒否します。事前に別途バックアップを保存してください。通常の明細保存・閲覧は旧IndexedDBを利用しません。

### MSAL v5・クリックジャッキング防御の運用

- MSAL Browserはnpmの**固定依存`@azure/msal-browser@5.30.0`**からビルド時に生成し、`dist/vendor/msal/msal-browser.bundle.js`に出力します。`public/vendor`へ手動コピーした旧バンドルは削除しました。`npm audit`、`package-lock.json`、`scripts/audit-msal.mjs`で追跡し、認証専用の`dist/auth/redirect-bridge.js`も同じ依存から生成します。
- **必須の移行作業**：Microsoft Entraアプリ登録のSPAリダイレクトURIへ、公開先の`/auth/redirect.html`を追加してください。`localhost`で試すなら`http://localhost:5000/auth/redirect.html`など、使用するオリジンのURIも個別登録します。ブリッジはMSAL専用であり、他のPayrollコードやSharedWorkerを実行しません。
- GitHub Pagesはアプリ側でカスタムの`Content-Security-Policy: frame-ancestors 'none'`や`X-Frame-Options: DENY`をHTTPレスポンスに設定できません。アプリ画面は起動前の`frame-guard.js`と保管庫解除時の埋め込み拒否で**補助的に**防御しますが、これはHTTPヘッダーと同等の保護ではありません。完全なフレーム制限を求める場合はヘッダーを制御できるホスティングへ移行し、通常画面は`frame-ancestors 'none'`、**MSALのリダイレクトブリッジページはサイレント認証用に別ポリシー**としてください。ブリッジにCOOPヘッダーを付けないでください。
- npmの依存更新時は`package-lock.json`までコミットし、`npm ci`で再現可能なビルドにします。MSALの未管理・手動配置JSを復活させないでください。`scripts/audit-msal.mjs --built`はビルド出力も検査します。

### 公開前のローカル防御と定期監査（導入が必要）

**公開リポジトリではpush後のCIは情報漏えいを取り消せません。** 初期設定として、まずMacの
`~/.config/payroll/private-terms.txt` に、リポジトリへ含めてはならない実名、住所、口座識別子などを1行1件で記入してください。このファイルは必ずプロジェクト外へ置き、Gitへ追加しないでください。

Gitleaksを導入後、`bash scripts/install-git-hooks.sh`を一度実行します。Gitの`core.hooksPath`を
`.githooks`へ設定し、コミット前は**実際のステージング内容**を、push前はGit履歴、依存、テスト、ビルド成果物を検査します。エラー時はコミット・pushを中断します。 `git -c core.hooksPath=...` や `--no-verify` 等でローカルフックは迂回可能なので、GitHub側でもmainのルールセットによる**直接push制限と必須ステータスチェック**を設定してください。

GitHub Actionsには同じ辞書を公開ファイルとして配置せず、リポジトリのActions Secret `PAYROLL_PRIVATE_TERMS_B64` としてBase64で登録します。Macで `gh` が使える場合は、次のように秘密の値を表示せず登録できます。

```bash
base64 < "$HOME/.config/payroll/private-terms.txt" | tr -d '\n' | gh secret set PAYROLL_PRIVATE_TERMS_B64 --repo oreno-payroll/oreno-payroll.github.io
```

GitHubウェブ画面から設定する場合は Repository Settings → Secrets and variables → Actions へ。**このSecretが未設定・空・不正ならCIは失敗し、デプロイしません。** 週1回の定期CI（UTC月曜00:19、日本時間月曜09:19）はnpm依存・秘密情報・全テストを再検査し、Pagesへの再デプロイは行いません。

`scripts/audit-dist.mjs` は `dist/` の全ファイルを公開ソースとnpmリソースからの厳密な許可リストに照合し、意図しないファイル、改変されたコピー、CSP欠落、生成JSの再ビルド不一致、既知形式の秘密情報と個別禁止語句を検出します。専用検査 `scripts/audit-ci-workflow.mjs` は、レビュー済みのワークフロー構造と実行ステップ、SHA固定、検査順序を確認します。

Gitフック・パターン検査・Gitleaks・辞書でも任意の個人情報を確実には検知できません。コミット前の最終目視、ブランチ保護、公開済み情報の失効・削除対応は引き続き必要です。またPlaywright実機E2E、実Microsoft/OneDrive接続試験、TypeScript実装の網羅的なコードカバレッジ・ミューテーション検査は現状の自動検証対象外です。

**旧検証スクリプトの整理：** IndexedDBの旧永続保存方式、PDF Service Workerの旧挙動、旧URL形式に依存する6本を廃止。成果物の機能確認に使える`verify-three-features.mjs`と`verify-calendar-feature.mjs`は現行仕様へ更新し、`npm test`へ組み込みました。

### PR必須のCIとGitHub Pages公開手順

- **普段の開発では`main`を直接変更しません。** `git switch main && git pull --ff-only` で更新後、`git switch -c feat/変更名` で作業します。コミット・`git push -u origin feat/変更名` は引き続きローカルフックを通し、`gh pr create --base main --fill` でPRを開きます。
- `.github/workflows/deploy.yml`の`security`ジョブは、`pull_request`・`main`への`push`・手動実行・週次監査で常に実行します。PR時はGitHub生成の**mainとの仮マージコミット**を検査し、秘密情報・過去履歴・依存関係・ビルド・`dist/`・全回帰テストをPASSさせます。PRからGitHub Pagesのアップロードやデプロイは行いません。
- `security`が失敗・未実施ならマージさせないよう、GitHub Settings → Rules → Rulesets → `protect main branch` で **Require a pull request before merging（承認0件）** と **Require status checks to pass（`security`、GitHub Actions発行元、Require branches to be up to date）** を有効化します。バイパス許可者は追加しません。**最初のPRの検証が済んでからルールを有効化**し、設定後はGitHubの画面から直接push拒否も確認します。
- デプロイは`security`成功を必要とする別の`deploy`ジョブで行います。検査ジョブが生成した**同じ`dist/`アーティファクト**だけをPagesに配信し、デプロイジョブでは再ビルドしません。週次監査とPRでは公開しません。
- ワークフロー全文の監査済みSHA-256を`scripts/audit-ci-workflow.mjs`に固定しています。CIの正当な変更でも明示的なレビューとハッシュの更新が必要です。`scripts/audit-pr-target.mjs`はPR仮マージの両親コミットを確認し、検査対象の一時Git参照を作ってGit履歴の検査漏れを防ぎます（公開リポジトリの履歴は書き換えません）。
- Actions Secret `PAYROLL_PRIVATE_TERMS_B64`は必須。**フォークからのPRにはGitHubがこのSecretを渡さないため、検査は安全側に失敗**します。外部PRを受け付ける場合はSecretsを渡さず成立する検査体系を別途設計してください。`pull_request_target`は利用しません。
- GitHubの管理者にはルールセットを変更する権限があるため、悪意ある管理者まで技術的に完全封鎖する構成ではありません。これは個人開発における誤操作や検査抜けを防止する仕組みです。

### セキュリティ検査と制限

- ホーム・アップロード・設定を含む全画面のCSPでJavaScriptの `unsafe-eval` を許可しません。使用中のPDF.js 6では旧 `isEvalSupported` オプションは存在しないため設定しません。PDF用WebAssemblyのため `wasm-unsafe-eval` は維持します。
- コミット直前の検査は `node scripts/audit-publish.mjs --staged` です。ファイル拡張子や秘密情報のパターンを検査しますが、氏名・住所・口座番号・給与金額を完全に見つけるものではありません。コミット対象とGit差分も必ず目視してください。
- Git履歴全体の追加監査は、Macで `brew install gitleaks` した後 `bash scripts/audit-history.sh` を実行します。`--redact` を指定し、検出した秘密文字列の表示を抑えます。出力をリポジトリ内に保存しないでください。過去の履歴に問題が見つかった場合は値の失効・再発行も検討してください。
- 旧8時間/2時間のタブ鍵キャッシュは使用せず、起動時に`sessionStorage`から破棄します。更新後に古いタブが残る場合は、全タブを再読み込みしてください。

### 運用と制限

- Financeと同じClient IDを利用する場合も、アプリの公開オリジンが異なればMicrosoft接続状態は個別に確認します。Payroll保管庫とFinance保管庫の復号パスフレーズは別々に管理してください。
- CSPはGraph、Microsoftログイン、OneDrive署名付きダウンロードURLに必要な接続先を許可します。
- 旧PDF Service WorkerのIndexedDBアクセスは廃止し、暗号化PDFをOneDriveから復号してBlob URLで表示します。PDF閲覧時の内蔵ビューアの保存時ファイル名は、旧名前付きURL方式と異なる場合があります。
- 初回利用前に**別のOneDriveアカウントを誤って選ばないこと**、**復号パスフレーズを紛失しないこと**に注意してください。
- `npm run check && npm run build && npm test` に加え、実際のMicrosoftアカウントを使うMac/GalaxyのE2E検証を行ってから運用に切り替えてください。

### 従業員の年末調整：原本PDF ZIPと年間課税支給額の照合

従業員・暦年を選択後、**「明細を追加・管理」内の「取り込み明細一覧」右上にある小さな「PDF一括DL」**から、その年度の保存済み原本だけをZIPで取得できます。出力ZIP内のPDFは平文、ファイル名には支給年月・給与/賞与区分を含みます。同じファイル名になる場合のみ末尾に番号を付け、確認ダイアログは表示しません。OneDrive上の暗号化ファイルは変更せず、各原本を復号後SHA-256で検証します。復元用バックアップとは別の形式です。

保存済み明細の一覧で×を押す操作は、**その場でOneDriveへ削除を送信せず**、削除予約として一覧から外すだけです。削除予約は同じ明細一覧の中に表示し、複数件ならまとめて折りたたみます。個別の「元に戻す」または「すべて元に戻す」で保存前に取り消せます。編集・新規取込・削除予約は共通の「すべて保存」で年度データへまとめて確定され、確認ダイアログは原則不要です。保存前にページを離れる場合は未保存警告を出します。別タブで対象の改訂番号または年度ファイルが変更されていた場合、競合として保存を拒否します。原本PDFをOneDriveのごみ箱へ移すのは年度データの保存が成功した後だけで、ごみ箱移動に失敗した場合は年度データを戻さず、整理未完了を明示します。

年間課税支給額は**支給日（暦年）**で集計し、保存済み給与・賞与の「課税支給合計」＋未支給分の保存済み見込みを表示します。「年間課税支給額の月別内訳を確認」から月ごとの実績・見込み・未取得・支給なしを検証できます。金額表示はブラウザ標準のテキスト選択に対応し、クリップボードを加工する独自処理は設けません。
